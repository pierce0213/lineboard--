# 图层 & 动画播放 · 可行性方案

> 目标读者：产品决策者（你）
> 结论一句话：**两者都可行，且都不需要推翻现有架构。** 图层是「中等改动 + 高风险点集中在存档格式」，动画是「低改动 + 纯渲染层叠加」。

---

## 一、结论先行

| | 可行性 | 改动性质 | 主要风险 | 建议 |
|---|---|---|---|---|
| **图层** | ✅ 可行 | 数据模型 + 渲染顺序 + 存档格式 | `packShapes` 分组 key 不加层号会**静默丢分层** | 一期做，但必须先立「兼容性红线」 |
| **动画播放** | ✅ 可行（成本更低） | 纯渲染层，**不动数据结构** | 导出 WebM 需实时录制、大画面掉帧 | 一期做「逐笔重放」，二期做「图层入场」 |

核心原因：现有代码已经**预留了两个关键钩子**——
1. 所有图形按「画出来的先后顺序」存在 `state.shapes` 数组里（`push` 追加），**动画要的时间轴信息天然存在，零成本**；
2. 渲染已经收口成 `buildLayouts()` → `paintFills/paintBlocks/paintStrokes`（`symmetry-draw.html:1902-1906`），**要插一层「按图层分组」或「按进度裁剪」只需改这一处**，不必碰 4000 行里的其他角落。

## 二、现状盘点（决定方案边界的事实）

| 事实 | 位置 | 对方案的影响 |
|---|---|---|
| `state.shapes` 是**扁平数组**，没有 layer / z-index 概念 | `state` @676 | 加图层 = 引入新维度，但可用「缺省值」做到零破坏 |
| 绘制顺序**按类别、不按图形顺序**：先全画填充 → 再全画色块 → 最后全画线条 | `render()` @1891-1906 | 「线条永远压在线条之上」是**刻意设计**。图层必须**在类别之内**生效（层内仍三类顺序，层与层之间才叠） |
| 对称是**渲染期派生**，不落数据（`pointMaps()` @964） | `pointMaps` / `mapSets` @1392 | 图层跟着源图形走，对称副本自动跟随，**零适配成本** |
| 撤销快照 = **整个 shapes 数组深拷贝**（`cloneShapes()` @1169，深度 40/80/120） | `pushUndo()` @1191 | 加图层后，**快照必须从「数组」升级为「文档」**，否则撤销会让图层结构错乱 |
| 存档 v2 把色块**按属性分组成块**（`packShapes()` @2309），key = 颜色+透明度+线宽+样式+格网+格距 | `packShapes` @2309 | ⚠️ **本方案最大的坑**：key 不含层号 → 两个图层里的同色色块会被并成一组，读档后分层信息丢失且**不报错** |
| 自动保存 key = `lineart-board-autosave-v1`，含 `ver` 字段（@2292） | `autosave` @4230 | 升到 v3 后旧自动存档要能读（新代码兼容旧格式即可，无需迁移脚本） |
| 命中测试 / 吸附缓存 / 格子索引都是**全文档线性扫描** | `hitTest` @1233、`buildSnapCache` @1007、`isCellFilled` @998 | 都要加「按可见层过滤」，否则会出现「看不见的东西删不掉」「吸附到隐藏层的点」这类幽灵 bug |
| 色块上限 `MAX_BLOCKS = 16000`，且对称会按份数打折 | `effectiveBlockLimit()` @667 | 需要决定：隐藏的层算不算进上限（建议算，数据结构不变，避免撤消/显示时突然超限） |

**现有测试资产**：127 项 CDP 无头 Chrome 端到端测试全绿（弧线 29 / AI 15 / reasoner 13 / IP 9 / 像素 27 / bug 25 / 还原 9）。这套基建可直接复用来验收新功能。

## 三、图层方案

### 3.1 三种路线对比

| | **A. 层内保持类别序**（推荐） | B. 真正的 z-order | C. 不做数据层，只做「分组选择」 |
|---|---|---|---|
| 做法 | 每个图形带 `layer` 号，层内仍「填充→色块→线条」 | 每个图形带全局 z，可任意上下穿插 | 图形打 tag，只用于批量选中/隐藏 |
| 观感自由度 | 高（够用：底色层、线稿层、上色层、标注层） | 最高 | 低 |
| 破坏现有保证 | 否（层内行为与今天完全一致） | **是**——「线条永远压在线条之上」失效，用户可能画出自己都看不清的图 | 否 |
| 改动面 | 渲染 + 存档 + 命中 + 吸附（6 处） | 上述 6 处 **+ 全部绘制函数 + 三处 z 排序 UI** | 仅 UI |
| 风险 | 中 | 高 | 低但价值也低 |

**推荐 A。** 理由：现有用户已经习惯「色块不会盖住线」这条心智模型（新手引导里专门写了这句，@622），B 会把它打破；而 A 已经能覆盖 90% 的真实需求（画人物：底层填色 / 中层线稿 / 顶层标注）。

### 3.2 数据模型（A 方案）

```js
state.layers = [
  { id: 0, name: '图层 1', visible: true, locked: false, alpha: 1 }
];
state.shapes[i].layer = 0;   // 缺省 0，旧档/新画的图形都落在第 0 层
```

- **层序 = 数组下标**：`layers[0]` 画在最底下，`layers[n-1]` 在最上面。
- **不引入 `zIndex` 字段**，上下移层就是数组 `splice`，少一个可失同步的状态。
- 图形不带 `layer` 字段时一律按 0 处理 → **旧存档不做任何转换即 100% 兼容**。

### 3.3 必须同步改动的 6 个点（漏一个就出幽灵 bug）

1. **渲染**：`render()` 把 `buildLayouts()` 改成「先按 layer 分组，再逐层跑三类 paint」。层间用 `ctx.globalAlpha = layer.alpha` 包一层。**这是唯一需要动渲染逻辑的地方。**
2. **存档 `packShapes`**：分组 key 追加 `sh.layer`，且输出顺序必须保证「同层相邻」，否则展开后图形顺序错乱会连带影响动画重放顺序。
3. **撤销快照**：`pushUndo/undo/redo` 从 `cloneShapes()` 升级为 `cloneDoc() → {shapes, layers}`。为了不改动 15 处调用点，建议保持 `pushUndo()` 签名不变，只改内部。
4. **命中测试**：`hitTest()` 跳过 `visible === false` 或 `locked === true` 的层。
5. **吸附与格子索引**：`buildSnapCache()`、`isCellFilled()`/`cellIndex` 按可见层过滤；`commitBrush()` 的「同格同色跳过／异色替换」**只在当前层内比对**（否则在图层 2 上色会误删图层 1 的格子）。
6. **当前层约束**：新图形/新色块落到 `state.currentLayer`；图形工具在锁定层上应给提示而非静默无反应。

### 3.4 UI 位置（两个选项）

- **选项 1 — 左侧面板新增一区**（与现有 6 个分区并列，rail 导航加一个图标）
  优点：复用现有组件与折叠逻辑，零布局风险。
  缺点：左侧已经很长，图层列表又要占高度，会把工具区挤下去。
- **选项 2 — 右侧浮动抽屉**（固定在画布右缘，独立滚动，可整体收起）
  优点：图层列表高度不受限，符合主流画图软件（PS / Procreate）的心智。
  缺点：需要新增一层布局与 CSS，窄屏（< 900px）要处理遮挡。

**倾向：选项 2**，并把「动画」面板也放进同一个抽屉的不同 tab —— 两者都是「结构型面板」，共用一套容器。

图层面板需要的操作：新建 / 删除 / 重命名（双击）/ 显示隐藏 / 锁定 / 不透明度 / 上移下移 / 合并到下一层 / 清空当前层 / 把选中图形移到其他层。

## 四、动画方案

### 4.1 三档，建议一期只做第一档

| | **① 逐笔重放**（推荐） | ② 图层入场 | ③ 关键帧时间轴 |
|---|---|---|---|
| 效果 | 画面按绘制顺序「长」出来，线条有笔迹生长感 | 每个图层按设定的方式登场（淡入 / 飞入 / 缩放 / 旋转 + 延迟） | 逐属性轨道、缓动曲线、可编辑关键帧 |
| 依赖 | 无（`shapes` 顺序现成） | 依赖图层功能先落地 | 依赖 ① + ②，还需时间轴编辑器 |
| 改动面 | `render()` 加一个进度参数 + 3 个 paint 函数加裁剪 | 再加「图层变换」层 | 新增大半个编辑器 |
| 建议 | **一期** | **二期** | 暂不做 |

### 4.2 播放引擎（机制）

```
anim = { playing, t0, dur, speed, loop, mode }
        ↓ rAF 每帧算出 progress ∈ [0,1]
        ↓ 唯一的进度裁剪函数：shapeProgressAt(sh) → 0..1
   paintFills / paintBlocks / paintStrokes 共用它
```

要点：
- **只有一处进度计算**（`shapeProgressAt`），三个 paint 函数共用。散落到三处必然出现「色块出现了线条还没长完」这类时序不一致。
- **生长效果如何实现**：现有图形全是折线点集（`pts`），按累计弦长裁剪即可得到「画到一半」的点集；弧线也是 poly，**自动兼容，无需特判**。色块按「格」逐个弹出，文字按透明度淡入。
- **播放期间**：禁用绘制交互、暂停自动保存、不进撤销栈、**动画状态不进存档**（只把 `dur/speed/mode` 这类轻量配置写进 settings）。
- **和对称的关系**：进度作用于源图形，镜像副本同步出现，天然正确。
- **性能红线**：16000 个色块逐格出现，3 秒内要每帧丢 ~180 格。建议按「组」而不是随机逐格——`packShapes` 已经给出了每组 `cells`，直接拿来做批次即可。大画面播放时应提示或自动降级为「按图层淡入」。

控制条：播放/暂停、进度拖拽、时长（2/4/6/8 秒）、循环、缓动开关、**导出**。

### 4.3 导出三条路

| 方式 | 依赖 | 优点 | 缺点 |
|---|---|---|---|
| **WebM（推荐）** | `canvas.captureStream()` + `MediaRecorder`，浏览器原生，零依赖 | 体积小、可直接发社交平台 | 必须**实时播放一遍**（6 秒动画就等 6 秒）；需 Chrome/Edge；Safari 支持有限 |
| GIF | 需内嵌编码器（gif.js 或自写 LZW，约 30KB） | 兼容性最好、图床通用 | 256 色有带宽、体积大、编码耗时 |
| PNG 序列帧（zip） | 零依赖 | 最稳、画质无损 | 用户需自行合成，体验差 → 只做兜底 |

**建议：一期做 WebM，二期补 GIF。** 同时加一个「导出透明底 PNG」的复选框（现在 `exportPNG` @2454 是白底，动画截图常需要透明底）。

### 4.4 与现有功能的交叉影响

- **撤销**：播放/导出不产生撤销步骤。✅
- **自动保存**：播放期间 `markDirty` 不触发，避免每秒写盘。✅
- **AI 生成 / 图片转填格**：新图形追加在数组尾部 → 天然出现在动画末尾，符合直觉，无需特殊处理。✅
- **色块压缩**：`packShapes` 已保证「组按首次出现位置插入」，读档后顺序与存盘前一致 → **动画重放顺序不会因存档往返而变**。这是现成代码已经做对的地方。✅

## 六、风险清单

| 风险 | 等级 | 对策 |
|---|---|---|
| `packShapes` 分组 key 漏加层号 → 分层静默丢失 | 🔴 高 | 一期必改；补「同色块跨层」的专项往返测试 |
| 撤销快照仍是「数组」→ 撤销后图层结构错乱 | 🔴 高 | 快照升级为 `{shapes, layers}`，一次性改内部实现、保留签名 |
| 「线条永远在最上层」被打破 | 🟡 中 | 层内保持现有三类顺序，不做全局 z |
| 命中/吸附忘记过滤隐藏层 → 幽灵 bug | 🟡 中 | 统一收口到 `isLayerActive(id)` 一个判断函数 |
| 大画面录制掉帧 → 导出视频卡顿 | 🟡 中 | 导出前提示；可选「按固定帧率逐帧 toDataURL」替代实时录制 |
| 后台标签页 rAF 被节流 → 录制出问题 | 🟢 低 | 导出前提示保持前台 |
| 左侧面板过长 + 新增两个面板 → 界面拥挤 | 🟡 中 | 用右侧抽屉 + tab；窄屏退回左侧折叠区 |
| 代码量继续膨胀变「屎山」 | 🟡 中 | 图层与动画各自独立成块，只通过 `buildLayouts()` / `shapeProgressAt()` 两个接缝接入；完成后跑一次 `html-app-audit` 的死代码与重复扫描 |

## 七、需要你拍板的 5 个决策点

1. **图层范围**：确认走 **A 方案**（层内保持类别序，不做全局 z）？
2. **UI 位置**：**右侧抽屉**（推荐）还是**左侧新增一区**？
3. **动画一期范围**：只做**逐笔重放**，还是连**图层入场**一起做？
4. **导出格式**：**WebM**（推荐）/ GIF / PNG 序列帧 / 先不做导出？
5. **品牌文案**：面板副标题现在是「无图层 · 线条连接 · 对称辅助」（@348），新手引导里也写了「没有图层概念」（@362）。加图层后这两处要改——改成什么由你定，或我按「多图层 · 线条连接 · 对称辅助」处理。
